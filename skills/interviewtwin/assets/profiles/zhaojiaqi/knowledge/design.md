# 用餐规划：设计原则与方案说明

来源记录：赵家奇确认的《餐小美统一事实稿》v2.1，第 12 节，2026-10-25。本文件保留用餐规划的细化说明。餐小美整体架构、三级意图、任务状态、工具分工、交易授权及结果验证的历史设计事实见history.md第6节；不能将这些已有设计改述为现在才提出的建议。这里额外展开的细节，不自动证明全部实现、实测效果或真实事故。

### 12.1 偏好：来源、强度和范围分别管理

规划综合用户本次明确要求、本人确认的长期偏好、系统根据历史行为形成的推测，以及实时业务约束。

- **来源**：用户明确表达、设置或对话确认、历史行为推测分别记录；推测不能覆盖用户明确设置。
- **强度**：安全限制、明确排除或必须满足的要求，与尽量满足的软偏好分开；“少吃面食”不能转成“禁食面食”。
- **范围**：长期、本次、指定日期餐段及明确有效期分别管理；“今天清淡一点”不自动长期保存，“以后尽量清淡”经保存确认后才成为长期偏好。
- **维度**：食材限制、饮食方式、口味做法、菜系与商家喜好、营养目标、份量与多样性、日期餐段、餐补及自付预算。无需用户填完所有普通喜好才能开始规划。

先满足适用硬约束，再依据用户明确优先级和候选信息权衡软偏好，不编造固定权重。历史点餐只能辅助排序，不能推断过敏；用户可纠正推测，不能用同批历史反复恢复已被否定的推测。

例如，“今天少安排面食”仅约束本次；“以后都少安排面食”进入长期保存确认。经常点米饭不等于不能吃面食。这样设计是为了避免临时表达污染长期推荐，并使用户可以理解和纠正系统认识。

### 12.2 记忆：适用范围不等于存储技术

长期／短期描述适用范围，结构化／文本／向量描述保存与查询方式，不能把长期记忆等同于向量库。

| 对象 | 设计中的管理方式 |
|---|---|
| 用户确认的长期偏好 | 结构化保存内容、对象、强度、范围、来源、状态和版本；适用硬约束完整读取 |
| 本次要求及例外 | 关联当前任务与餐段，不自动继承到新任务 |
| 方案与生成依据 | 保留当前方案、历史版本、使用的偏好版本和业务快照；旧版本可查但不可直接执行 |
| 对话与摘要 | 用于理解上下文，不替代授权记录、约束字段和交易状态 |
| 余额、菜单、订单及支付结果 | 以对应业务系统为权威来源，按时效刷新，不能靠聊天或向量召回推断 |

保存偏好与重做餐单是独立操作。修改偏好后先识别影响，不静默覆盖已选餐品，不自动取消已有订单。删除偏好后停止用于后续规划，历史记录仍按当时依据解释。

上述细化说明不提供具体服务端选型、跨设备同步或索引机制的验证结果。历史架构中短期记忆、长期偏好、持久化Task State与实时业务系统的职责，按history.md第6节说明；本地实现样例的验证状态不用于否定历史设计。

### 12.3 模型、程序与 Workflow 分工

设计采用固定业务阶段、局部模型决策、确定性校验和授权后的交易执行相结合的方式。

- 模型负责理解自然语言、提取候选条件、从业务候选中安排餐品、提出局部调整及解释取舍。
- 程序与业务工具负责核验候选有效性、日期餐段、金额、约束、订单冲突和版本一致性。
- Workflow 负责在有效授权和业务前提下推进交易，结果以业务返回为准。

模型提出方案不代表方案已经合规；“我已校验”不能替代真实校验结果。MCP 是工具接入方式，接入 MCP 本身不证明后端是真实业务系统。

整体模型、Skill、Workflow和工具分工按history.md第6节的历史架构说明；本节局部细化不用于推定所有历史版本同时具备每一项细节。

### 12.4 局部修改：保留已接受内容，再检查整体影响

用户要求“只换周四晚餐”时，先锁定其他未授权修改的餐段，只调整目标部分；调整后复核整体预算、约束及重复搭配。若必须联动其他餐段或增加自付，先说明影响并取得必要确认。

当前可执行方案保持唯一版本，历史方案可查看。迟到的旧生成结果、旧卡片及旧确认不能覆盖或执行新的方案。

这样处理是为了减少用户重复审核，也避免每次追问都推翻已接受的选择。

### 12.5 确认与执行：确认绑定具体内容

规划范围确认、长期偏好保存、方案确认、取消原订单和支付分别具有不同含义，不能互相替代。

确认需关联用户、地点、需求、方案和业务依据。关键内容发生变化时重新校验，必要时重新确认，不能拿旧确认执行新内容。“方案不错”不等于同意新增自付、取消订单或扣款。

已有订单区分保留、追加和替换，不把规划餐段数直接当作新增订单数。程序校验与授权交接成功，也不等于实际创建、取消或支付成功。

### 12.6 失败与证据不足：保留真实状态

- 菜单查询失败与查询成功但无候选分开；无解餐段明确保留，不能悄悄少安排一餐后宣布全部完成。
- 预算不足先在原约束内调整；仍无解则说明受影响范围，不自动增加个人支付或放宽硬约束。
- 过敏等安全证据不足时不能依据菜名、图片或“未列出”判定安全，也不能用一次用户确认代替缺失证据。
- 交易超时表示结果可能未知，先核查原操作，不直接创建第二笔订单；部分成功时保留成功记录，暂停或恢复未完成部分。
- 已取消的真实订单不能仅通过修改本地状态假装回滚；恢复成功同样需要结果证据。

超时核实、幂等约束和部分成功处理属于历史架构中的异常处理设计；这些原则和示例不等于真实生产事故记录，也不提供某次事故已验证的修复结果。
